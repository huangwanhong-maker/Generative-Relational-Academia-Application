# Adversarial conformance review — feature gauntlet + skeleton audit

Rulings key: **(a)** safe as-is · **(b)** safe only under the stated reformulation (layer named) · **(c)** must be refused (constraint named, with a reason a user would accept). Layers: *record-facet*, *sidecar-facet*, *workspace-facet*, *local-plane-facet*; action classes: *recording*, *applicative*, *bridge*.

---

## Part I — 38 things people will predictably ask for

### (a) Safe as-is

1. **Node detail panel showing signed fields** (act, target, relation, trigger, disposition, performer, attestation, identifier). Record-facet, read-only projection. Already settled in the design note. Nothing computed may appear beside it.
2. **Cite-this-transition / export citation.** Emits identifier + CiTO term. Serves C10 and C12 directly. Record-facet + applicative copy action.
3. **Color/shape nodes by act or disposition.** Both vocabularies are closed and part of the signed payload; a legend over 8 acts and 3 dispositions is a projection, not a judgment. Record-facet.
4. **Vocabulary validation on entry** (reject unknown relation, flag `local:` as unbound). `resolve_relation` already does this; presenting unbound values as bound is the violation, refusing them is not. Recording-action plumbing.
5. **Counts inside one open trajectory's detail view** ("this question has 4 challenges, 2 unresolved"), shown only when that trajectory alone is open. Explicitly permitted by C6's carve-out — but see skeleton finding S8 for the badge trap.
6. **Bundle export / take-the-record-and-leave.** C10 is not just permitted, it is owed. Any friction added here is itself a finding.

### (b) Safe only under reformulation

7. **Meeting RSVP.** Reformulation: a personal *add-to-calendar* entry in the requester's own local plane (`.grrp/`-adjacent, never exported). Refused variant: any shared roster of who intends to come — a pre-attendance list is an attendance list with a tense change. Layer: local-plane-facet.
8. **Activity feed.** Reformulation: *chronology of a single project*, ordered by `performed`, no per-person facet, no cross-project merge, no recency badges — exactly the design note's "calendar of chronology." Refused variant: any feed filterable by performer or unioned across projects (C6, per-person timeline). Layer: record-facet.
9. **Notifications.** Reformulation: local-plane alerts derived from record changes the user can already read ("a new transition took your state as parent"), computed client-side, never stored, no delivery/read receipts anywhere. Refused variant: server-side notification log or "seen" state — that is the event plane exported. Layer: local-plane-facet.
10. **Importance stars / pins.** Reformulation: a *private pin*, local-plane only, invisible to every other party, no count, never exported. Refused variant: shared or aggregated stars (C6 scalar over trajectories). Layer: local-plane-facet.
11. **Search.** Reformulation: filtering plus deterministic orderings (chronological, lexical); per-query text match may order results but the score is ephemeral, never displayed as a number, never persisted as an index, never applied to performers, and must work offline (C9, C11 — the search cache is rebuildable from files). Refused variant: "relevance" as a standing ranking over trajectories (C6 in a trench coat). Layer: applicative, rebuildable cache.
12. **Task lists.** Reformulation: notes in a *workspace* folder — mutable, unbundled, self-maintained; a person may write "I will address the objection." Refused variants: assignment of tasks *to* other people with tracked completion status (an obligations ledger is C6-adjacent accountability plumbing and pressures fabricated closure), and any rollup of open/closed tasks. Layer: workspace-facet.
13. **Deadlines.** Reformulation: the calendar of commitments already sanctioned — `release_at`, embargo expiry, shorten-only (sidecar-facet); plus private local-plane reminders. Refused variant: a deadline attached to a challenge or question ("resolve by Friday") — the vocabulary keeps `unresolved` precisely so that closure is never owed on a date.
14. **"Mark resolved."** Reformulation: a *recording action* — "record a `decision` (or `verification`) that addresses this challenge," a full new transition with content, citing the challenge's state (C3, C4). The disposition of the old transition never changes; the graph shows the answer standing next to the objection. Refused variant: any state flip on an existing node (C3 + closed dispositions).
15. **Approval workflow.** Reformulation: approval-as-record is an `agrees`/`supports`/`confirms` connection transition by the approving party, or attested registration (C2) — visible endorsement, never a gate. Refused variant: approval as a precondition for recording or publishing — C10 says nobody's permission is required to continue the record, including yours. Layer: recording.
16. **Private comments.** Reformulation: workspace notes — mutable, unsigned, never bundled; they enter the record only via the bridge (cited by hash inside a real act). Refused variant: a private thread stored *in* the record with narrowed visibility — disclosure widens only (C7), so the record cannot carry content that is secret-by-audience. Layer: workspace-facet.
17. **Comment threads on a transition (public).** Reformulation: threads are a *presentation* of `repliesTo` chains — connection transitions with content, signed, ordinary nodes. Refused variant: a lightweight unsigned comment table beside the record — that is a parallel, unattested record of scholarly speech (C1, C2, C12). Layer: record-facet over recording actions.
18. **Delete.** Reformulation: three honest deletions exist — (i) anything applicative, freely (that layer "costs nothing to delete"); (ii) *content* removal via redaction with a stated ground from `REDACTION_GROUNDS`, skeleton and signatures staying valid (C8); (iii) *standing* removal via a `retracts` transition (C3). Refused variant: deleting a transition (C3, no exception).
19. **Project archiving.** Reformulation: record-side closure is a `release` act or simply stopping; UI-side, hide the project from *my* workspace list (local-plane). Refused variant: unpublishing — C7, disclosure never narrows; see item 30.
20. **AI involvement.** Reformulation: `trigger=ai_suggestion` on a transition performed and signed by a human — the vocabulary already says a model "may occasion a transition and may not author or register one." Refused variant: model-as-performer or model-as-registrar (C2 — attestation between a person and their own tool is theater). Layer: recording.
21. **Auto-summaries.** Reformulation: optional, offline-capable, regenerable applicative caches, visually marked as unsigned derivations, never bundled, never the default face of a node (the signed content is the identity; a paraphrase presented as the node misattributes words to a signature). System must be fully usable with the feature off (C9). Layer: applicative cache under C11.
22. **Watch lists.** Reformulation: a private local-plane bookmark list — my attention, on my machine, visible to no one. Refused variants: "followers of X," follower counts, "who watches this" — a directory of attention is a monitoring record whichever direction you read it (C6 + the event-plane ruling). Layer: local-plane-facet.
23. **@mentions.** Reformulation: a mention inside content is just content; a mention in a workspace note may raise a *local* notification for the mentioned party's own client. Refused variant: mention analytics or a who-mentions-whom graph (C6, person-centric graph).
24. **Transition templates / prefill.** Reformulation: applicative prefill of vocabulary fields for a real act the user is already performing. Refused variant: template-driven prompting that solicits transitions ("weekly update template") — an operation whose purpose is that a record exist (C1).
25. **Draft transitions.** Reformulation: a draft is a workspace file — mutable, unsigned, invisible to the record — until the moment of recording; there is no "draft" status in the record, because an unsigned record state would let signatures attest to things that later changed (C3, C8). Layer: workspace-facet → recording.
26. **Undo.** Reformulation: applicative undo freely; record undo is `retracts` (cito:retracts) — a new transition that says so, forever (C3).
27. **Sync/backup service.** Reformulation: transport of plain files and bundles (git, rsync, sneakernet); the service is a courier, never the system of record, and everything works with it absent (C9, C11).
28. **Duplicate / "related question" suggestions.** Reformulation: optional applicative aide, offline-degradable; acting on a suggestion is a human-performed `connection` with `trigger=ai_suggestion` if a model surfaced it. Refused variant: auto-created connection transitions (C1 + performer must be a person).
29. **Onboarding tutorial.** Reformulation: the tutorial drives a disposable demo repository, never the user's real record — practice transitions in a real trajectory are records manufactured so records exist (C1). Layer: applicative.

### (c) Must be refused

30. **Unpublish.** C7. *"Others may already have continued from what you shared; the protocol promises them the ground under their work cannot be pulled back — redaction of content is available, retraction of standing is available, un-happening is not."*
31. **Person/profile node.** C4 + C6 + the monitoring ruling. *"The moment a person is a node, everything they did aggregates to them, and the graph becomes a dossier; the record attaches to states, and a performer is a key on a transition, not a place things pile up."* (The one survivable residue — a key-fingerprint verification panel — is applicative and is not a node.)
32. **Attendance lists.** Settled outright: the event plane is never exported. *"A log of who was present is a monitoring record by construction — the single failure with the largest consequence for participants — so presence is never written down, anywhere, in any layer that travels."*
33. **Progress bars.** C6, and the disposition design. *"A progress bar is a scalar over a trajectory and a promise of completion; this record exists to say honestly that most objections stay unresolved, and a bar stuck at 80% punishes exactly that honesty."*
34. **Kanban states.** Closed dispositions + C12 (parallel vocabulary) — the brief's own instinct is right. *"A column is a disposition vocabulary in disguise: 'done' is a fourth disposition the protocol deliberately refused, and dragging a card is an unsigned, unattested reclassification of a signed event."*
35. **Edge weights.** C6, plus reification. *"A semantic edge is already a signed transition; a weight would be an unsigned number ranking relations against each other, which is exactly the scoring the record refuses."*
36. **Reactions/emoji.** C6 + C2 + C1. *"A reaction is an endorsement with no content and no attestation that exists to be counted; the protocol's version of 👍 is an `agrees` transition where you say why, under your key."*
37. **View counts.** C6 + monitoring. *"Counting reads requires logging readers — a record of attention on both sides of the number — and no count over participants is ever shown."*
38. **Contributor leaderboards.** C6, verbatim. *"Any ranking of participants converts the record into the metric it was built to escape; there is no screen that answers 'who did most.'"*
39. **Merge/combine of branches.** C5, including the word ban. *"Divergent states both remain true records of what was understood; a transition may take both as parents and say, in content, what it makes of the divergence — but nothing collapses them, and no interface surface ever offers the word."*
40. **Edit-in-place on record content.** C3. *"The signature covers the bytes; a corrected understanding is a new transition with `modifies` or `replaces`, so the record shows both that you were wrong and that you noticed."*
41. **Cross-project dashboard.** C6. *"Two projects' numbers on one screen is a comparison whatever the labels say; projects are opened one at a time, and each shows only its own chronology."*
42. **Per-person timeline / filter-by-performer view.** C6 + design note's explicit ban. The files are portable and grep-able (C10) — anyone *can* compute this — but the application must not offer the affordance. *"The record cannot stop you from studying a person; it can decline to be an instrument built for it."*
43. **"You haven't recorded in N days" nudges, streaks, badges.** C1 (and C6 for streaks). *"An operation that exists so that a record exists is the definition of the failure; the record is a byproduct of work, and silence is a permitted state of work."*
44. **"Last active" / presence dots.** Monitoring + C6. *"Presence indicators are attendance streamed live."*
45. **Graph-metric overlays** (centrality, node size by degree, influence). C6; design note: "a node with many edges is a node with many edges." *"Any computed prominence is a ranking over trajectories with extra steps."*
46. **Color-by-performer on the canvas.** C6/monitoring: it converts the graph into a per-person activity map at a glance. Performer stays where it is — in the detail panel of one node at a time.
47. **Time tracking.** C6 + monitoring + C1. *"Hours are a scalar over a participant, gathered by watching them."*

## Part II — Audit of the skeleton itself

**S1. Occasion-kinds risk violating C1 at the constructor.** If "meeting" is a node kind, someone will build a *create meeting node* button — a node existing so the occasion is on record, with zero acts behind it. The precedent already decides this: a meeting that produced nothing recorded is a calendar entry. The spec must state that occasion-kinds are **derived** groupings (transitions sharing a cited artefact + trigger), never directly creatable, and that an occasion with no transitions does not exist in the graph.

**S2. Occasion rollup = attendance by reconstruction.** CRediT contributions per act are legitimate (C12), but an occasion-kind view that unions contributors across its transitions into a "participants" panel has rebuilt the attendance roster from signed parts. The occasion view may list its *transitions*; it must never present a merged roster of people. This is the single most likely quiet violation in the whole skeleton.

**S3. The user's own example, "join-meeting action," is a trap the skeleton doesn't defuse.** Join must be a pure launcher (open URL, add to own calendar) that writes nothing anywhere — the moment joining leaves a trace, it is presence logging. Name this explicitly in the action spec, because "join" naturally suggests membership state.

**S4. "Bridge" cannot be a free-standing action class.** The precedent says the bridge *is an act*: material joins the record only when a transition cites it. If bridge exists as its own button producing a bare citation-transition with no other content, that transition exists solely so a record exists (C1) and cites nothing specific in the sense C4 demands. Fix: bridge is a *parameter of recording actions* (an `artefacts` picker inside a real act), not a sibling class — or the spec must require that every bridge rides on a genuine act with content.

**S5. Administrative operations have no home.** `vocab.py` defines `OPERATIONS` (disclosure_changed, redaction, key_rotation, fork_declared, attribution_contested, binding_recorded, deposit_recorded) and `REDACTION_GROUNDS`. The skeleton's three action classes (recording / applicative / bridge) cover none of these: they are not acts, not applicative (they have record-plane consequences), not bridges. Either add a fourth class — *administrative* (sidecar/operations plane, widen-or-remove-content-only, grounds required) — or the redaction path (C8's whole point) will get bolted on ad hoc.

**S6. Presentation names over acts strain the vocabulary's own rule.** "Act-kinds as they read to a person" is fine until a friendly label drifts ("Objection" for `challenge`, "Answer" for `decision`) and becomes a de facto parallel vocabulary (C12; vocab.py: never present a value as something it isn't). Rule to add: presentation labels map 1:1, the protocol term is always inspectable one gesture away, and labels are never persisted into anything that travels.

**S7. Structural edges "no identity, no components" needs its justification stated, or it will be reverted.** Someone will want to *challenge a parent link* ("this doesn't actually follow from that") and will ask for edge identity to do it. The right answer exists and should be written in: the parents list is part of the child's signed payload, so you challenge the **child transition** (C4 gives you the specific state). Without this paragraph, edge identity gets added "just for commenting" and reification leaks into structural edges.

**S8. The C6 carve-out will leak through badges.** "Counts within one trajectory, shown without comparison" — but a canvas showing many trajectories, each node wearing a "3 challenges" badge, *is* comparison by juxtaposition. The spec must scope counts to the single-trajectory detail context (panel of one selected thing), never to decorations rendered simultaneously across the graph.

**S9. Semantic edges inherit "every component a node gets" — including local-plane calendar.** Mostly free and correct (reification pays off), but audit the inheritance rather than granting it wholesale: a calendar facet on a relation is meaningless surface area, and unused surfaces are where the next feature request lands. Grant components per kind, by argument, not by inheritance.

**S10. Material-kinds referencing doi/arxiv/url must degrade offline.** C9: an external-work node may *hold* a resolvable reference but must render fully (identifier, citing transitions) with no network. Live metadata fetch is an optional applicative enhancement, cached under C11.

**S11. The refusal list is incomplete and asymmetric.** It refuses "mark-answered" without naming the legitimate neighbor (a `decision`/`verification` transition citing the challenge — item 14), which invites implementers to conclude challenges are dead ends. And it omits refusals this review found load-bearing: no view counts or read logs, no per-person filter/timeline (already banned in the design note but absent here), no reaction counts, no relevance-as-standing-index, no presence indicators, no occasion roster (S2). A refusal list that undersells is a refusal list that gets "extended" by whoever draws the next screen.

**S12. One wording nit with teeth.** The brief says semantic edges get workspace storage "for free." Nothing near C1–C12 is free; each inherited component either survives the same twelve tests independently or it doesn't ship. Recommend the spec's own language never uses "for free" — it is how the applicative layer's mutability gets mistaken for a general license.
